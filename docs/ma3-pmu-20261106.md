# MA3-PERF PMU probe — cache, branches, denormals, divider, 2026-11-06

**Question.** After the [vector lanes](ma3-vector-lanes-20261106.md), where do
the remaining cycles go? Specifically: cache misses, branch mispredictions,
floating-point assists (denormal handling) and the divider.

**Answer.** The remaining time is arithmetic, not memory or control flow:

- **Floating-point assists:** zero in every case on both engines.
- **Cache misses:** a few percent at most.
- **Branch mispredictions:** 1–2% of vector time.
- **Divider:** the largest identifiable item, an estimated 8–15% of vector
  time. Each division must stay a true division for bit-exactness.
- **BCS:** adds about 1.1 M cycles per 8-voice block when it is on. That is
  the largest scalar block left.

## Method

`driver/probe_ma3_pmu.c` (`make … build/…/probe_ma3_pmu`, not part of `test`)
uses the same workload as the bench: 8 held slots, wet effects, 128-frame
blocks, ten patch/BCS cases, the AUTO (vector) and SCALAR engines. It counts
user-space Haswell events per render block, one event group at a time with
cycles as leader, on the same deterministic workload. No block was
multiplexed, and the PCM matched between engines.

| Group | Events (raw config) |
|---|---|
| branch | instructions; `BR_INST_RETIRED.ALL_BRANCHES` (0x00c4); `BR_MISP_RETIRED.ALL_BRANCHES` (0x00c5) |
| cache | `L1D.REPLACEMENT` (0x0151); `L2_RQSTS.MISS` (0x3f24); `LONGEST_LAT_CACHE.MISS` (0x412e) |
| assist | `FP_ASSIST.ANY` (0x1eca); `ARITH.DIVIDER_UOPS` (0x0214) |

`--calibrate` checks each event against a known trigger. Values are per trigger:

- 1e6 random branches: 0.500 misses.
- 1e6 subnormal multiplies: exactly 1.000 assist each.
- 1e6 `divss`: 1.000 divider uop each.
- 1e6 dependent loads to random lines in 64 MiB: `LONGEST_LAT_CACHE.MISS`
  1.001 and 1.003 in two runs; L1D replacements 1.85 (adjacent-line
  prefetch).
- `MEM_LOAD_UOPS_RETIRED.L3_MISS` (0x20d1) gave 0.92 and 0.55 in two runs, so
  it was dropped in favour of `LONGEST_LAT_CACHE.MISS`.

**Host conditions matter.** A first pair of runs, made while a browser was
playing media on the same physical core (CPU 2 and its SMT sibling CPU 3),
moved cycles by up to 66% and cache counts by up to 15x between runs. The two
runs reported below were made with every browser closed, on CPU 2, with sleep
inhibited. Run to run they agree to 0.47% in cycles, 1.4% in branch misses,
0.16% in divider uops, and 0% in instructions, branches and assists. The cache
counts are small enough that their percentage spread looks large in absolute
terms. Cycles match the integrated A/B, for example Tepih with BCS off at
1.501 against 1.517 M and Granica with BCS on at 2.911 against 2.907 M.

Run: `build/ma3-pmu-20261106-01/` (`calibrate-{1,2}.csv`, the contaminated
`run.csv` and `run2.csv`, the quiet `quiet{1,2}.csv`, `sha256.txt`).

## Reading

Shares are upper bounds from published Haswell latencies, assuming no
out-of-order overlap. The real cost is lower.

- **Denormals: none.** `FP_ASSIST.ANY` is 0 in all 40 runs. The existing tiny
  flushes already keep subnormals out, so FTZ/DAZ would gain nothing and is no
  reason to change the numerical contract.
- **Memory: minor.** LLC misses are at most 17 per block. L2 misses are a few
  hundred. The vector engine replaces 3–4x more L1D lines than the scalar one:
  each sample touches eight voices' `ma_synth` state, the lane bank and the
  lane inputs. Even counted as a full L2 hit each (about 12 cycles), that is
  at most 5–8% of vector time.
- **Branches: minor.** The vector engine retires 4–5x fewer branches than the
  scalar one. Mispredictions are 0.6–0.8% of branches, at most 1–2% of vector
  time at about 16 cycles each.
- **Divider: the largest identifiable item.** The vector engine issues 28–44 k
  divider uops per block, compared with 68–110 k for the scalar engine. At
  Haswell's 256-bit divide throughput that is roughly 8–15% of vector time.
  Divisions cannot become reciprocal multiplies without changing bits. Some
  can still be skipped exactly when no lane needs them. One example is
  `ml_mix`, which always evaluates its raster-branch division; another is
  `ml_poly_blep`, which evaluates both edge divisions when either edge is live.
- **BCS: the largest scalar block left.** BCS-on cases cost about 1.1–1.2 M
  more vector cycles per block than BCS-off: about 1,100 cycles per
  voice-sample, and about 40% of a BCS-on vector block. BCS is a per-voice
  integrator, independent across voices, so lanes can carry it like the
  stages already moved.
